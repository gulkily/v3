## Verified project facts

### Public records and derived views

- Public content records live under `records/` in the writable canonical Git
  repository. Posts, public keys, identity bootstrap records, approvals, and
  reactions are represented as plain-text records.
- The SQLite read model is derived from those records.
- Static HTML is also derived state. It is published as an atomic static
  release, not treated as the source of truth.

### Commands

- `./v3 rebuild` is the primary CLI shorthand for rebuilding the SQLite read
  model. It dispatches to `scripts/rebuild_read_model.php`.
- `./v3 build-static` builds a candidate read model and all static pages, then
  publishes the static release. It is the command that accurately represents
  rebuilding both SQLite and static HTML.
- Therefore, do not label one arrow to both SQLite and static HTML with
  `./v3 rebuild`.

### Identity and signatures

- A member who chooses browser identity generates and keeps an OpenPGP private
  key in the browser. The normal signed-write flow sends a detached signature,
  canonical record, and public identity reference; the server verifies the
  signature against the published public key.
- Do not imply that every public post is signed. Anonymous posts remain
  supported. Say “signed public writes” or “a member’s signed writes.”
- The server does have a distinct `reply-agent` private key when automatic
  agent replies are used. It is a server agent key, not a member key.

### Private state and secrets

- Member OpenPGP private keys are not kept in the public record or application
  checkout.
- The server can have private material. LLM provider credentials normally live
  in `../forum-private/secrets.php`, outside the application checkout. Private
  runtime state lives under `state/private/`.
- `state/` is ignored by `.gitignore`, so
  `state/private/agent-reply/` is outside Git as well as outside `public/`.
- It is accurate to say that operator credentials and private workflow state
  live outside `public/` and Git. It is not accurate to say that no secret can
  exist on the server.

### Overview heading

Use:

How it works

### Card 1

Heading:

Public records live in Git

Body:

Posts, public keys, and identity events are stored as plain-text files under
`records/`, one file per record, in Git. The SQLite database is built from
those files and can be rebuilt with `./v3 rebuild`. Static HTML is built and
published with `./v3 build-static`.

This is the one intentional change from the supplied feedback. It avoids the
incorrect claim that `./v3 rebuild` rebuilds static HTML.

### Card 2

Heading:

Identity is an OpenPGP key

Body:

Each member who uses browser identity has an OpenPGP key pair. The private key
stays in the member's browser. The public key and fingerprint are published,
and a member's signed public writes can be verified against them.

The “signed” qualifier is required because anonymous posts are supported.

### Card 3

Heading:

What stays out of the public record

Body:

The server does not generate or store member private keys. Operator credentials
and private workflow state are kept outside `public/` and outside Git.

This wording is verified. Do not broaden it to say that the server has no
secrets: the optional LLM and reply-agent features need private server-side
material.

- label the records-to-SQLite arrow `./v3 rebuild`;

actual CLI behavior. If the visual design needs one shared label, use only
`./v3 build-static` and explain that it rebuilds both derived outputs.
