# Backlog view

Purpose: Show the open feedback items as one list that people and agents can sort, filter and start work from, so picking the next thing does not mean reading files or tag pages.
Scenario: The maintainer opens Tools → Backlog on his phone. The list shows items that can start (ready and untriaged), the best impact for the least effort first. He taps Effort, then Bugs; the address reads `/backlog?sort=effort&kind=bug`. He ticks two related bugs and presses Start. The start page lists both, with Agent decides chosen (One-shot and Staged cycle are the other choices), and a prompt of a few lines that names the procedure and the two item files. He copies it into an agent, which builds both as one cycle and opens a pull request. An agent without a browser reads the same list at `/backlog.txt?sort=effort&kind=bug`, or runs `./v3 feedback list --sort=effort --kind=bug` in a checkout, and gets the same prompt from `/backlog/start.txt?items=<ID>,<ID>` or `./v3 feedback start <ID>...`.

The list is the [feedback items](feedback_items.md) in the site's own checkout, so it is as fresh as the last deploy; the page states the version it read. It exists while `FORUM_BACKLOG_ENABLED` is on (off by default, meant for sites that develop the software) and anyone who can read the site can read it.

Words in the address: `sort` (`salient`, `entered`, `touched`, `effort`, `impact`), `order` (`newest`, `oldest`), `show` (`can-start`, `waiting` for blocked items, `open`, or one workflow value), `kind` (`all`, `bug`, `feature`, `other`) and `claimed` (`show`, `hide`). A word at its default stays out of the address; an unknown word falls back to the default and the page says so. Effort lists the lowest `Estimate` first and impact the highest `Impact` first, with items that have no value after those that do. Salient ranks by impact divided by effort, counting a missing value as 0.5. The order word decides ties by touched date (created date for entered).

Start takes one item or several; several become one cycle, one branch and one pull request. The mode is Agent decides (the default, `auto`, which leaves one-shot or staged to the agent under `AGENTS.md`), One-shot or Staged cycle, and the prompt opens with "Please". Every prompt asks the agent to work in a clone and open the pull request itself, not to hand over patch files, and to stop and say what to connect when it cannot clone or push. A prompt for several items also asks the agent to say so before building when they do not belong in one pull request. A plain form sends `items[]=A&items[]=B` and the server redirects to `?items=A,B`, so the start page has one readable address with or without scripts. Closed and unknown IDs are named and left out. On a site whose profile names a claims thread, Start also claims the picked items, rows show who holds them, and `claimed=hide` leaves held items out; see [work claim](work_claim.md). On a site with none, starting records nothing, and the procedure's check of the item in a fresh checkout and of open branches and pull requests is the only guard against two agents doing the same work.

The three text routes are sent with `Cache-Control: no-cache`.

Boundary: a list of parked plans is planned as the next cycle ([checklist](../plans/backlog_checklist.md)). Values are changed in the item files, not from the page.
