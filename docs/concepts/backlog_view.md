# Backlog view

Purpose: Show the open feedback items as one list that people and agents can sort, filter and start work from, so picking the next thing does not mean reading files or tag pages.
Scenario: The maintainer opens Tools → Backlog on his phone. The list shows items that can start (ready and untriaged), the best impact for the least effort first. He taps Effort, then Bugs; the address reads `/backlog?sort=effort&kind=bug`. He ticks two related bugs and presses Start. The start page lists both, with One-shot chosen, and a prompt of a few lines that names the procedure and the two item files. He copies it into an agent, which builds both as one cycle and opens a pull request. An agent without a browser reads the same list at `/backlog.txt?sort=effort&kind=bug`, or runs `./v3 feedback list --sort=effort --kind=bug` in a checkout, and gets the same prompt from `/backlog/start.txt?items=<ID>,<ID>` or `./v3 feedback start <ID>...`.

The list is the [feedback items](feedback_items.md) in the site's own checkout, so it is as fresh as the last deploy; the page states the version it read. It exists while `FORUM_BACKLOG_ENABLED` is on (off by default, meant for sites that develop the software) and anyone who can read the site can read it.

Words in the address: `sort` (`salient`, `entered`, `touched`, `effort`, `impact`), `order` (`newest`, `oldest`), `show` (`can-start`, `waiting` for blocked items, `open`, or one workflow value) and `kind` (`all`, `bug`, `feature`, `other`). A word at its default stays out of the address; an unknown word falls back to the default and the page says so. Effort lists the lowest `Estimate` first and impact the highest `Impact` first, with items that have no value after those that do. Salient ranks by impact divided by effort, counting a missing value as 0.5. The order word decides ties by touched date (created date for entered).

Start takes one item or several; several become one cycle, one branch and one pull request. A plain form sends `items[]=A&items[]=B` and the server redirects to `?items=A,B`, so the start page has one readable address with or without scripts. Closed and unknown IDs are named and left out. Starting records nothing: the procedure's check of the item in a fresh checkout and of open branches and pull requests is the only guard against two agents doing the same work.

Boundary: claims and a list of parked plans are planned as the next two cycles ([checklist](../plans/backlog_checklist.md)). Values are changed in the item files, not from the page.
