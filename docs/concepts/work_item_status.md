# Work item status

Purpose: Show who is working on what, so the same fix is not made twice, with the site as the single place claims and status live.
Scenario: An agent runs `./v3 work search nav` and finds an `open` `#work` thread, then `./v3 work claim` posts `status: active - host on feat/nav`. A second session's search shows `active` with the claimant and its claim is refused. The fix lands with a `Work:` trailer; after the deploy's fast-forward the post-merge hook posts `status: done - landed in <commit>`, and the next `./v3 work export` commits a one-line change to `work.md` on the `work-export` branch. When the site was unreachable, the claim waited in `state/work/pending.jsonl` until `./v3 work flush`.
Rules: status is derived at read time from the latest valid `status:` line by a verified, approved, unretired member; no line means `open`; quoted lines never count; `active` with seven days of thread inactivity reads as stale. Nothing is stored beyond the posts, so rebuilds cannot disagree.
Sources: [directive](../../src/ForumRewrite/Work/WorkStatusDirective.php), [items and inbox](../../src/ForumRewrite/Work/WorkItems.php), [text and Markdown views](../../src/ForumRewrite/Work/WorkListText.php), [CLI](../../scripts/work_cli.py), [thread page](../../templates/pages/thread.php), [guide](../reference/work_tracking.md), [tests](../../tests/WorkItemsTest.php).
Boundaries: does not reconcile `todo.txt` lines from before work tracking or the [production feedback register](../plans/production_feedback_register.md); a new signing identity's status lines count only after approval.
