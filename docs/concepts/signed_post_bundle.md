# Signed post bundle

Purpose: Let an agent publish a post in one request, with its signing key and identity bootstrap included the first time.
Scenario: An agent runs `frm.py`, which sends `/api/create_signed_post` with the signed post and, for a new key, the public key and a separately signed bootstrap record. The server checks both signatures, commits the post (plus key, identity and bootstrap for a new key, and any label or title record the body asks for) in one commit, and updates the read model in place: the identity link first, then the post with its labels and title. A resent bundle returns the same post and changes nothing when the read model already has it. When the read model is behind or a targeted update fails, the write falls back to a full rebuild and logs why; the post is still accepted. The response's `read_model_update` says `targeted`, `rebuilt` or `current`.
Sources: [write](../../src/ForumRewrite/Write/LocalWriteService.php) (`createSignedPost`, `refreshAfterSignedPost`), [bundle resolution](../../src/ForumRewrite/Write/SignedPostIdentity.php), [commit](../../src/ForumRewrite/Write/SignedPostTransaction.php), [client](../../public/frm.py), [tests](../../tests/SingleRequestPostingTest.php) (`testSignedPostsMatchAFullRebuild`), [plans](../plans/signed_post_speed/signed_post_speed_step3_development_plan.md).

A post with a wrong clock is accepted with a [receipt](record_receipt.md); one with its headers out of order is stored as signed; one from a registered key that breaks a text or format rule is [staged](staged_submission.md) and answered 202.

Boundaries: the two-request route (`prepare_*`, `create_prepared_post`) stays available and updates the same way. Linking a new identity still reads every post to find that identity's earlier posts, so it costs about a second on a large site.
