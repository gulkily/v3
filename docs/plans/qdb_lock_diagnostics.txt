Confirmed code bottleneck:
LocalWriteService::createIdentityBootstrap holds the execution/publication
locks across commit and synchronizeIdentityDerivedState. Its incremental path
calls IncrementalReadModelUpdater::applyIdentityLink, whose transaction calls
refreshProfileState. That loads all profiles and posts, derives approval/counts,
updates every profile and calls linkIdentityActivity for every profile.
linkIdentityActivity updates activity WHERE author_identity_id = identity ID;
ReadModelSchema has no index on that field. At the reported scale, each identity
can cause roughly 3,835 scans of roughly 18,853 activity rows. Actual stage
timings and current production lock-holder identity remain unverified.

During the canonical-commit-to-metadata interval, ordinary read requests see
a head mismatch and wait for the execution lock in ensureReadModel. They can
time out before the registration completes even though SQLite reads work.
Repeated full rebuilds are therefore not required to explain the outage.

Immediate containment proposed: temporarily reject POST requests to
/api/prepare_identity, /api/create_identity, /api/link_identity and /account/key
(including its trailing-slash form) in Apache before PHP dispatch. Existing
in-flight operations must finish; this does not release their locks. Preserve
the restored QDB SetEnv configuration. No production change has been performed.

Permanent fix should bound identity-update work and address the missing index,
with required schema version/spec/startup regression changes for any index
change. Approval propagation and existing-identity linking must remain correct.
