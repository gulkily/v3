## Stage 1 - Restrict account key approval paths

- Changes: Added the default-enabled `FORUM_ALLOW_NON_OPERATOR_CROSS_ACCOUNT_APPROVAL` setting and shared approval policy. With the setting disabled, members retain new-account sponsorship and approval of their own additional keys; root-seeded operators retain cross-account authority. Direct/manual approvals and invitation redemption recheck the current policy under the write lock. Stale read models fail closed. Targets must match their canonical bootstrap and profile.
- Changes: Generic posting rejects identity protocol tags, and generic finalization rejects prepared protocol records while retaining ordinary thread/reply support. Signed flag changes require actual root-seed authority rather than approval labels. Existing grants are not re-evaluated when the setting changes.
- Changes: Fixed same-second invitation replay so issuance precedes redemption even when random record IDs sort in the opposite order. Full/incremental projections and the writer share the ordering rule; same-second revocation conservatively precedes redemption. This dependency bug was exposed by the signed acceptance/rebuild test.
- Verification: Six policy tests cover the role/account matrix, live toggles, competing first-key claims, stale metadata/markers, canonical seed mismatches, protocol endpoint bypass attempts, invitation issuer/recipient restrictions, and same-second replay ordering. A signed invitation smoke test verifies acceptance-time denial, successful retry when permitted, and grant retention across a restricted rebuild.
- Verification: The final targeted run of policy, feature flag, invitation UI, signed approval/invitation, prepared post, signed flag-change, and approval rebuild tests passed. `git diff --check` passed. The earlier broad run executed 153 tests: 147 passed and six failed. Four prepared-post regressions were corrected and passed on rerun. The vote-caption failure also reproduces against planning commit `febc1e03`; the task-queue failure has existing checkout history dating to October 9 and remains unresolved (it passes in the isolated baseline directory).
- Notes: Production was not changed. Real browser review flows, durable acceptance receipts, expiry-independent invitation history, account/operator history, and deployment/rollback verification belong to stages 2–6. Do not treat this stage as completion of the approved vertical slice.

## Stage 3 - Durable acceptance evidence and stable invitation replay

- Changes: Added repository-owned ApprovalAcceptance receipts bound to exact grant bytes, acceptance time, account/key, authorizer, classification, count, authority, and effective policy. Direct/manual and invitation grants commit the receipt with the grant/signature without changing signed bytes. Receipts validate identities, time, grant binding, and signed review context where present; absent legacy evidence remains unknown.
- Changes: Failed acceptance writes unstage/remove incomplete grant files; a committed outcome is preserved if reporting fails. Exact signed direct retries recover committed success without duplicate grants. Existing projection-failure messages retain the committed-write distinction.
- Changes: Full and incremental projections share InvitationApprovalReplay. Receipts supply acceptance time rather than preparation time; legacy creation dates are replay evidence only, not claimed acceptance dates. Expiry is compared with historical event time instead of today's clock; later revocation cannot remove a receipted grant. Both projections validate available direct receipts.
- Changes: ArchiveRecordCatalog recognizes and validates receipts for trusted repository restores; remote content imports explicitly exclude this authority family.
- Verification: Final targeted run passed 36 tests across ApprovalAcceptanceTest, ApprovalPolicyTest, InvitationIssuanceTest, RepositoryArchiveImportCommandTest, ContentImportPlannerTest, RepositoryArchiveValidationTest, and six exact WriteApiSmokeTest methods. Coverage includes delayed/pre-expiry versus post-expiry acceptance, unknown legacy receipts, tampered bytes/context, an injected Git commit failure with clean retry, duplicate signed retry, signed invitation restore from tar.gz followed by rebuild, full/incremental parity, and projection-failure handling. An initial parity failure exposed an invalid posts.source_path query; reusing the canonical path resolver fixed it and the final suite passed. `git diff --check` passed.
- Notes: No database migration or production changes. Receipts are repository-owned evidence, not a new member-signed authority primitive; repository restore remains trusted administration. Account/operator presentation and release checks remain stages 4–6.

## Stage 4 - Account key history

- Changes: Added shared ApprovalHistory lookups and a common history partial on classic/Forte username and profile pages. Paginated account history shows approved keys, approver, known acceptance time, first-key/own-account/cross-account classification, operator overrides, count/policy snapshots, and grant/receipt links. Missing legacy acceptance facts stay unknown; root seeds are identified without inventing acceptance times. Receipt facts retain the original account/approver usernames when current names change.
- Changes: Profile API and CLI audit report the same acceptance evidence; compact profile/user summaries link to full history. Existing audit current-state review hints remain separately labeled and do not become confirmed violations. Source-path validation permits receipt links under existing site-access rules.
- Changes: Approval invalidation now includes the username, every same-account profile, and Forte variants; invitation acceptance uses the same invalidation path. History pages cap key pages at 100 (default 50) and candidate grant reads at 100 per key; ordinary bootstrap replies are filtered before the cap. No new public feed or device/IP data.
