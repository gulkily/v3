## Completion Contract

- Normal entry: with high-traffic mode on, a member or an agent posts a thread or a reply.
- End-to-end outcome: the thread page is rendered fresh and swapped in before the poster's response returns. The first load after posting shows the post, in any browser.
- Recovery: if the render cannot run, the post still saves. The route is queued, and the next cron run renders it even if the cached file looks fresh. `./v3 high-traffic refresh /threads/<id>/` stays the manual fix.
- Deployment check: on zenmemes.com with the mode on, an agent reply through `frm.py` shows on the maintainer's phone without turning the mode off.
- Release condition: merged, deployed, and the deployment check passed.

## Key Risks

- **Slower posting.** One render is added to each post while the mode is on. Early validation: Stage 3 times a long-thread render on the production host with `./v3 high-traffic refresh`. Mitigation: if too slow, move the render after the response is sent; the queue still covers it.
- **An older render wins the race.** A cron render that started before the post can swap in the old page afterward. Early validation: a Stage 1 test holds the page lock during a write. Mitigation: a busy page lock queues the route, and the queued entry records the write time, so cron renders again.
- **Hint queue drops the route.** `HighTrafficRefresh::hint` and `hints()` skip and delete routes whose file is under 60 seconds old, which is exactly the case after a stale render. Early validation: Stage 1 test. Mitigation: a hint from a write counts as due until the page file is newer than the write.
- **A refresh error fails a saved post.** Mitigation: the refresh runs after the write lock is released and catches every error; the post result is already final.

## Stage 1

**Estimate: 0.10**

- Goal: one call refreshes a thread page after a write, or queues it.
- Dependencies: none.
- Expected changes: add `HighTrafficRefresh::afterPost(string $threadId): string`, returning `refreshed`, `queued`, `skipped` or `inactive`. It does nothing when the mode is off or the page is not cached; a missing page is generated by its first reader as today. Otherwise it calls `HighTrafficCache::generate` with force. A refusal or error queues the route. Change `hint` to accept a write-time stamp that bypasses the freshness check, and change `hints()` to keep such an entry until the page file is newer than the stamp.
- Verification approach: new `HighTrafficTest` cases: a cached page is replaced and the old file served until the swap; a held page lock gives `queued` and leaves a write-stamped hint; cron keeps that hint while the page is under 60 seconds old but older than the stamp; mode off gives `inactive` and touches nothing.
- Estimate details (extended mode only): driver: hint semantics shared with the browser's 60-second hint; uncertainty: whether `generate` with force can run cleanly from a web request outside cron.
- Risks or open questions:
  - Impact: a changed `hints()` could re-render routes endlessly.
  - Early warning / validation: test that a hint is dropped once the page is newer than its stamp.
  - Mitigation: browser hints keep today's behavior; only write-stamped hints use the new rule.
- Canonical components/API contracts touched: `HighTrafficCache::generate` (reused unchanged), `HighTrafficRefresh::hint` and `hints` (extended), `HighTrafficRoute::canonical` (reused).

## Stage 2

**Estimate: 0.10**

- Goal: every post write refreshes its thread page.
- Dependencies: Stage 1.
- Expected changes: `LocalWriteService::withTimedWriteLock` gains a refresh step after the lock is released, beside the offline snapshot queue. It runs only when the write's result asks for it. `createThreadForAuthoringMode`, `createReply` (including agent replies), `createPreparedPost`, `createSignedPost` and `createPreparedPostFormat` set that request with their thread ID. Tags, likes and `setThreadSubjectIfEmpty` (the media-preview subject fill) do not. The step's time goes into the result's `timings`; any error goes to the error log.
- Verification approach: a `LocalWriteService` test with the mode on in a temporary site: a reply replaces the cached thread page; a tag write leaves it alone; a forced render failure still returns a saved post and leaves a queued hint. Run with the smoke set: `./v3 test --smoke HighTrafficTest HighTrafficPublicationTest AgentPostingApiTest`.
- Estimate details (extended mode only): driver: five write entry points and the already-posted early returns; uncertainty: whether the test harness can enable the mode without a real access log.
- Risks or open questions:
  - Impact: a write path missed here keeps today's stale page.
  - Early warning / validation: test each entry point through its public method.
  - Mitigation: the request is set where each path builds its success result, so a new post path is easy to spot in review.
- Canonical components/API contracts touched: `LocalWriteService::withTimedWriteLock` (extended), the post write methods named above (extended), `HighTrafficSafety::beforeWrite` and the `dirty` marker (unchanged).
