## Routing Rule

Use one-shot implementation for work that is operational, diagnostic, already
specified narrowly, or isolated to one small code path with clear verification.

Use docs/fdp/FEATURE_DEVELOPMENT_PROCESS.md when the work changes product
semantics, crosses multiple ownership boundaries, needs explicit user approval,
adds new canonical/read-model contracts, or has open design questions.

## P0: Do First

1. Secret hygiene from todo.txt
   - Route: one-shot operational cleanup.
   - Why: imported notes indicate live-looking provider keys in todo.txt.
   - Plan: remove secrets from tracked notes, rotate exposed keys outside this
     repo, and keep only non-secret feature-request text.
   - Verification: search tracked files for known key prefixes and confirm no
     secret values remain. Do not paste secrets into docs, commits, or logs.

2. Fail-fast production busy page
   - Route: one-shot production config.
   - Source: docs/plans/production_instant_busy_page_simple_plan_v1.md.
   - Plan: set FORUM_EXECUTION_LOCK_TIMEOUT_SECONDS=0 in production, reload the
     runtime, hold the lock with flock, and verify a contending dynamic request
     returns the existing HTTP 503 busy page immediately.
   - Escalate to FDP only if this requires changing the global locking contract.

3. CSS and recursive asset-fingerprint hygiene
   - Route: one-shot code fix plus cleanup script/guidance.
   - Why: no literal "no css loaded yet" string exists in current PHP templates,
     but public/assets contains recursively fingerprinted files, and
     AssetFingerprint::copyFingerprintedAssets() will fingerprint already
     fingerprinted asset names.
   - Plan: make copied asset discovery ignore already fingerprinted filenames,
     clean duplicate generated assets after confirming source/generated
     boundaries, and add smoke coverage that rendered CSS resolves and asset
     filenames contain only one hash segment.
   - Verification: php tests/run.php plus focused asset fingerprint tests.
   - Escalate to FDP only if the fix expands into service-worker/PWA caching.

4. Confirm automatic agent work is disabled where intended
   - Route: one-shot production verification.
   - Why: the imported stall investigation found a real boolean parsing bug; the
     current code handles PHP booleans, but production must be on the fixed build.
   - Plan: verify private config/environment values, confirm new post pages no
     longer render automatic data-agent-reply-work when disabled, and use browser
     Network timing to identify any remaining 5-15 second request.
   - Escalate to FDP only if the remaining fix changes async agent-reply product
     behavior beyond the already implemented request/worker path.
