Ranking basis: User-visible/rebuild exposure, measured materialization and independence of correction; not predicted host speedup. Eight tracked findings, including inherited/overlapping causes, not eight new discoveries.
Rank 1: LBS01 QDB welcome first, then separate numbered-list/random/search slices. Strong current body-count evidence, ordinary public and shared build exposure; highest semantic risk if broadened all at once.
Rank 2: LBS02 offline candidate retention. Strong current selection evidence; narrow streaming step preserves pins and can reduce retention before tackling SQL projection.
Rank 3: LBS04 tags-index narrow projection. Streaming already fixed retention, but bodies still cross PDO; lower risk if isolated from RSS/Forte/custom query consumers.
Rank 4: LBS07 source-history lookup. Direct rebuild relevance and avoidable full output; validate deep-history measurements before estimating savings. Do not conflate with delivered indexCommits fix.
Rank 5: LBS05 pending-user count. Small independent fix, source-only evidence; may be chosen before larger work for low implementation complexity.
Rank 6: LBS06 standard username inactive tab. Source-only, identity-history growth; preserve Forte consumers and aggregate totals.
Rank 7: LBS03 tag-route enumeration. Smaller metadata allocations, old evidence only; optional profile work already default-off.
Rank 8: LBS08 historical scoring audit. Operator-only, inherited evidence; necessary full examination but unnecessary simultaneous body retention.
Recommendation: Start a separately approved QDB welcome selection cycle using LBS01's parity contract. This audit authorizes no remediation, automated CI detector, schema/index change or deployment.

Finding: LBS01
Ownership: Inherited M02, same root cause; not a new discovery
Status: Measured reader/policy slice; broader consumers source-traced
Source: src/ForumRewrite/ReadModel/ThreadRepository.php fetchThreads/boardRowsSql; src/ForumRewrite/Qdb/QdbExperience.php welcome/random/search/eligibleQuotes; src/ForumRewrite/Qdb/QdbBoardPolicy.php paginate; src/ForumRewrite/Http/BoardPageController.php board/fetchBoardThreads/boardList/listPage
Consumers: Application -> QdbExperience -> welcome, random, search; latest/top/leetness -> BoardPageController. Standard list board selects 50 non-pinned rows after fetching/sorting all rows. StaticArtifactBuilder renders shared/QDB routes through Application. Shared method use does not mean identical selection rules.
Work: Complete joined rows including bodies before eligibility/filter/sort/slice; 10000 body rows/20,480,000 body bytes for 25 results (60 MiB PHP peak). Welcome first-five slice has same materialization. SQL scanned rows and end-to-end wall time remain unknown.
Invariants: Exact QDB suffix regex eligibility; retracted and identity-tag exclusion; liked-view root score; pinned precedence; top/oldest/newest/leetness tie-breaking; welcome recent order differs from board creation order; news creation order; clamped numbered pages/counts; search stripos semantics; random sampling without replacement. Preserve existing links and viewer reaction lookups after selection.
Smallest correction: QDB welcome bounded recent/news hydration plus exact count first, without changing other ThreadRepository consumers. Later independent slices for numbered lists, random and search; standard list board separately. Do not replace all fetchThreads calls with a universal LIMIT.
Required checks: IDs/order/count parity against current logic on mixed eligibility, malformed tags, pins, equal dates/scores, page boundaries and news; fixed-result body-transfer scaling, real welcome/build-static flow, failed-build leaves active release intact. Random distribution and non-ASCII search need their own tests before changing those paths.

Finding: LBS06
Status: Source-traced inactive-tab overfetch; unmeasured

Other directory coverage: ForteUserDirectoryController loads approved/pending summary rows for category counts/sorting, with SQL MIN/MAX activity aggregation rather than all post bodies. Its complete directory is an exception, not evidence that all directory queries are efficient. Large selected-user histories remain a separate size dimension.

Finding: LBS02
Ownership: Inherited M04, same root cause
Status: Measured current offline selection method; adjacent paths source-traced
Source: src/ForumRewrite/Offline/PublicOfflineSnapshotBuilder.php visibleThreadRows/snapshotThreadRows/buildWhileLocked/visiblePostsForThread/insertUnavailableExpansions; src/ForumRewrite/Host/StaticArtifactBuilder.php buildFromReadModel; src/ForumRewrite/TaskQueue/TaskQueueWorker.php runOfflineSnapshotPublication
Consumers: Static build and queued offline publication; saved offline_reader.js boardRows/tagGroups/savedTagPage consume the resulting database.
Work: 1000/10000 rows, including previews, materialized to select 201; PHP peak 4/24 MiB. Default recent limit is 200 plus ALL pinned threads. Selection currently loops all candidates even after filling recent slots to find pins. Selected-thread posts and global expansion candidates are additional unbounded dimensions, not measured by this probe.
Smallest correction: Stream ordered candidate rows into pinned and bounded-recent collections, preserving current parser/eligibility/order. This bounds ordinary candidate retention but still scans/transfers previews and retains all pinned rows; disclose that limit. A later narrow metadata/SQL selection can avoid unnecessary preview hydration after exact predicate parity is established.
Required checks: Old/new IDs/order for mixed visibility, all-pinned, zero/one/many pins, pins older than recent window, effective derived tags and retracted/excluded structural content; full publication at size boundary, prior snapshot preserved on failure, saved online/offline navigation. Preserve valid expansion dependencies and unavailable markers; never cap pins silently. Full large-thread and expansion cases remain unmeasured.
Browser boundary: offline_reader.js boardRows maps all saved thread metadata; savedTagPage then slices 25 after grouping. Snapshot byte cap/default recent limit reduce normal input, but all pins and selected-thread sizes can grow. Complete downloaded snapshot/update merging is its current offline contract. Browser allocation/network growth was not measured; do not claim the live TagPage bound applies to offline JavaScript.

Finding: LBS07
Ownership: Residual of inherited M06 source-history branch; not a new independent discovery
Status: Source-traced, unmeasured
Source: src/ForumRewrite/ReadModel/ReadModelBuilder.php preloadSourceCommitShas; src/ForumRewrite/Canonical/CanonicalRecordRepository.php preloadLegacyPostCreatedAts
Consumers: Full rebuild/build-static indexing posts, thread labels, reactions and feature-flag changes; canonical legacy timestamp preload.
Work: exec captures complete Git log path output before selecting requested paths. preloadSourceCommitShas retains first/newest match per requested path and continues after all paths resolve. Legacy timestamp preload intentionally retains oldest add event and cannot use the same early-stop rule. Prior CommitHistoryReader optimization fixes indexCommits, not these methods.
Smallest correction: Stream source-commit lookup and stop only once all requested paths have their first valid match, preserving Git ordering/merge semantics and error outcome. Legacy oldest-add pass needs streaming through complete history, independently.
Required checks: Merges/combined diffs, renamed/deleted/re-added paths, missing/shallow history, Git failure, unchanged source commits/activity ordering; compare total Git output read and PHP/RSS on deep histories with few requested paths. Preserve current failure fallback; intentional early process termination must not masquerade as Git error. No speedup quantified here.
