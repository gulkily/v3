Finding: M01
Priority: High; full rebuild
Evidence: Reproduced at 128 MiB with no artificial retained memory.
Location: src/ForumRewrite/ReadModel/ReadModelBuilder.php:199-275 and rebuild():85-101
Entry points: ./v3 rebuild and build-static candidate creation; delete-record post-removal refresh -> ReadModelBuilder::rebuild -> indexPosts.
Problem: indexPosts accumulates every parsed post including full prose, sorts the collection, then creates another array of post rows plus thread summaries. The returned corpus remains live through approval/profile/reaction/activity work. The previous fix releases it only after activity insertion, so it does not bound these earlier phases.
Reproduction: 40000 canonical posts, each with a 2048-byte body and ordinary headers, exhaust memory during indexPosts at line 211. The test repository has no Git history, isolating this from history-buffer costs.
Direction: Stream source records into the derived database; retain only the metadata required by each subsequent pass. Use bounded database passes for ordering and derivation. Preserve sequence ordering, author attribution, approvals and removal structure; do not drop content to meet the budget.

Finding: M02
Priority: High; static rendering and ordinary QDB reading
Evidence: Reproduced through both the shared reader and QDB buildFromReadModel at 128 MiB without padding.
Location: src/ForumRewrite/ReadModel/ThreadRepository.php:20-45; src/ForumRewrite/Http/BoardPageController.php:300-310; src/ForumRewrite/Qdb/QdbExperience.php:151-162,186-190,238-240; src/ForumRewrite/Qdb/QdbBoardPolicy.php:49-61
Entry points: QDB welcome/latest/top/leetness/random/search; build-static shared/QDB routes -> BoardPageController or QdbExperience -> ThreadRepository. Shared RSS also uses the reader; its output contract needs separate review.
Problem: All thread rows, full root bodies and previews are fetched before filtering, sorting and pagination. Hydration/filtering also constructs arrays. Welcome, latest/top/leetness, random, search and related shared readers inherit this shape; selecting 5, 10 or 25 displayed quotes does not limit query memory.
Reproduction: 40000 quotes with 2048-byte bodies and 1024-byte previews exhaust memory at ThreadRepository.php:26. Actual QDB static rendering reaches the same failure. This is not dependent on detail-page prebuilding.
Direction: Select/count/order eligible quote IDs in SQLite and hydrate only the displayed set. Preserve exact sort tie-breaks, quote eligibility, search, random behavior, scores and pagination. Audit RSS separately rather than silently truncating it.

Finding: M03
Priority: High for large archive commits; residual risk in the just-fixed evidence phase
Evidence: Measured growth and reproduced failure under explicit headroom pressure.
Location: src/ForumRewrite/Activity/ActivityService.php:856-941; src/ForumRewrite/ReadModel/ActivityEvidenceIndex.php:28-58
Entry points: Rebuild and incremental activity indexing -> ActivityEvidenceIndex::refreshBatch -> ActivityService::primeCommitEvidence; selected Activity commit detail uses sourceCommitFiles.
Problem: 200-row and 32-commit batches do not bound a single commit's manifest. primeCommitEvidence captures all diff-tree lines, groups them, then retains parsed per-file arrays. sourceCommitFiles similarly captures a whole manifest. A large import commit may be loaded again in subsequent row batches.
Reproduction: One synthetic 100000-path commit peaks at 60.01 MiB for priming alone. With 80 MiB retained to simulate other application state, it fails in parseCommitFiles at line 934. This does not claim the live QDB commit has 100000 paths.
Direction: Stream Git output and select evidence relevant to the current activity batch; preserve rename/signature/key evidence and missing-history behavior. Full commit-detail views need their own bounded delivery contract.

Finding: M04
Priority: High for static publication growth
Evidence: Measured peak and reproduced failure with explicit headroom pressure.
Location: src/ForumRewrite/Offline/PublicOfflineSnapshotBuilder.php:247-289,303-337
Entry points: build-static -> StaticArtifactBuilder::buildFromReadModel -> PublicOfflineSnapshotBuilder::build -> snapshotThreadRows / visiblePostsForThread / insertUnavailableExpansions.
Problem: The default 200 recent threads are selected only after every visible thread has been fetched. All pinned threads are retained. A selected thread's full post set and all reply-agent expansion candidates are also fetched as arrays. The 100 MiB output-file limit applies after these input allocations and therefore is not a PHP memory limit.
Reproduction: Selecting 200 recent plus one fixture-pinned thread from the 40000-quote dataset peaks at 94.01 MiB. With 64 MiB retained, it fails at line 259 before limiting the result. Huge individual threads and expansion corpora were inspected but not separately executed.
Direction: Select bounded recent rows and stream pinned rows; process thread posts/expansion checks without materializing entire candidate collections. Preserve pinned-content and snapshot-size behavior.

Finding: M05
Priority: Medium; rebuild growth beyond post bodies
Evidence: Source inspection, not an independently reproduced failure.
Location: src/ForumRewrite/ReadModel/ReadModelBuilder.php:358-484,501-574,580-724; src/ForumRewrite/ReadModel/VerifiedAttribution.php:94-112
Entry points: Rebuild/delete-record/static candidate creation -> ReadModelBuilder label/subject/reaction passes and VerifiedAttribution::markActivity.
Problem: Label/reaction/subject passes retain complete row sets and parsed records alongside lookup maps, viewer-tag rows and accumulated activity events. Attribution marking fetches every relevant named-identity reaction. Some builder queries use PDO's default FETCH_BOTH, adding numeric keys as well as associative keys. Releasing the outer post collection later does not remove these intra-phase peaks.
Direction: Stream row iteration and insertions, bound grouping/sorting, avoid redundant associative/numeric row storage, and move retained derivation state to the existing derived database where appropriate.

Finding: M06
Priority: Medium; long-history repositories
Evidence: Source inspection, not an independently reproduced failure.
Location: src/ForumRewrite/ReadModel/ReadModelBuilder.php:1103-1140,1335-1394; src/ForumRewrite/Canonical/CanonicalRecordRepository.php:70-103
Entry points: Rebuild/static candidate creation -> preloadSourceCommitShas / indexCommits; indexPosts -> CanonicalRecordRepository::preloadLegacyPostCreatedAts.
Problem: Git log output is captured completely in PHP arrays for commit indexing, source-commit lookup and legacy timestamps. Source lookup can read the entire relevant history even when current paths would be resolved by an early portion. Memory grows with history length and changed paths, not only current corpus size.
Direction: Consume Git output incrementally; bound error output and retain only unresolved-path/result metadata. Preserve merge/rename semantics and normal actionable errors.

Finding: M07
Priority: Medium; high-traffic maintenance
Evidence: Reproduced oversized allocation on a tiny input under explicit headroom pressure.
Location: src/ForumRewrite/Host/HighTrafficRefresh.php:19; default in HighTrafficCache.php:22
Entry points: ./v3 high-traffic run -> HighTrafficRefresh::run -> popular.
Problem: popular() uses stream_get_contents with the configured 16 MiB read ceiling even for a one-line access log. This repeats the exact temporary-buffer pattern fixed in RecordLimits. The configuration permits up to 10 times that default, so configured bounds alone are not a 128 MiB safety guarantee.
Reproduction: A one-line access log with 114 MiB retained fails attempting to allocate 16777248 bytes. No production log was read.
Direction: Read only available suffix bytes with small chunks, preserving suffix/line bounds and partial-line handling.

Finding: M08
Priority: Medium; Fastmod historical audit/backfill preparation
Evidence: Reproduced at 128 MiB without padding.
Location: src/ForumRewrite/Scoring/FastmodHistoricalAuditService.php:22-55
Entry points: ./v3 fast-score audit and backfill preparation -> scripts/fast_score.php -> FastmodHistoricalAuditService::audit.
Problem: audit() fetches every post body and accumulates unrated candidates. Even when fetchAll narrowly fits, the retained corpus leaves insufficient space for normal per-row work and candidate growth.
Reproduction: The 40000-quote dataset exhausts memory during score lookup at SqliteFastScoreStore.php:22 while the all-post array is retained. That allocation site is not evidence that the individual lookup is large.
Direction: Stream posts and batch/persist candidate selection, preserving content hashes and exact work-state counts.

Finding: M09
Priority: Lower; static route enumeration
Evidence: Measured overhead, no failure in the exercised case.
Location: src/ForumRewrite/Host/StaticArtifactBuilder.php:290-326,701-725
Entry points: build-static -> StaticArtifactBuilder::buildFromReadModel -> fetchVisibleTagRoutes and optional detail-ID enumeration; detail routes depend on the existing prebuild flag.
Problem: Thread/post IDs and tag routes are discovered using whole-table arrays followed by filters/maps. Their rows are much smaller than full quote rows, but memory still scales with corpus size.
Reproduction: Tag-route discovery for 40000 threads peaks at 22 MiB to return five routes. It is not the largest observed allocation.
Direction: Stream enumeration/deduplication and use count queries for progress reporting; preserve route inventory and all themes.

Finding: M10
Priority: Medium; malformed canonical/imported record handling
Evidence: Reproduced below the existing 16 MiB record ceiling without padding.
Location: src/ForumRewrite/Canonical/GenericTextRecordParser.php:20-28
Entry points: Canonical record reads during rebuild/import -> typed parser -> GenericTextRecordParser::parse; malformed headers fail before ordinary duplicate-header rejection.
Problem: explode creates an array for every header line before duplicate/invalid headers are rejected. The byte limit does not bound PHP per-element overhead.
Reproduction: 2500000 repeated short header lines plus a body total 12500006 bytes. Parsing fails with memory exhaustion at line 28, rather than the intended duplicate-header exception. This is deliberately invalid input, not a representative ordinary quote.
Direction: Iterate header lines without first allocating all of them, preserving existing record limits and exact validation behavior.

Secondary screening: ContentImportPlanner retains whole import plans; RepositoryArchive bounds byte reads but retains up to 100000 entry records, and score-supplement decoding retains bounded-by-count arrays. These are scale risks needing dedicated acceptance cases, not reproduced findings in this audit. Image ZIP restore bounds individual entry sizes before allocating and uploads bound dimensions before decoding; do not classify every file read as unbounded. High-traffic renderer output has byte/time checks; tiny metadata/schema fetchAll calls are not corpus-sized reads. SignatureCheckCache uses SQLite rather than an unbounded PHP result map. Existing Forte lazy-pane work does not fix the QDB whole-list reader.

Recommended order: First address M01/M02/M03/M04 as separate bounded work slices across rebuild, evidence and rendering/offline publication, using the proposed lower-budget acceptance matrix below. M07/M10 are small independent fixes. Then address history/reaction/scoring/route growth (M05/M06/M08/M09). Preserve the 128 MiB incident reproductions as historical evidence. Do not treat another successful tiny fixture build as production-scale acceptance.
Verification contract proposed: Record phase peaks on representative quote, reaction and Git-history fixtures; exercise one large commit, one large thread, malformed-but-byte-bounded input and retry after interrupted candidate builds. Verify identical visible content, scores, signatures, ordering, pagination and artifact inventory. Tests use explicit per-process limits; changing the host configuration is a separate operational decision. Preserve canonical formats and content-size limits. Apply CONTRIBUTING schema-change requirements if a selected fix introduces new schema or query dependencies.

Budget discussion: 2026-10-30 UTC
User question: for the qdb audit, it feels like 128mb is still way too high for this applicatin, what do you think a reasonable limit is that we should target?
Proposed targets: Ordinary public requests should normally peak at or below 16 MiB with a 32 MiB test ceiling; rebuild/static maintenance should normally stay at or below 48 MiB with a 64 MiB test ceiling. These are engineering proposals, not approved requirements or measured production guarantees. The existing 128 MiB ceiling remains the incident reproduction condition.
Design requirement proposed: For a fixed requested page/batch size and comparable individual record sizes, memory should remain approximately flat as total corpus size grows. Track CPU/I/O separately; bounded PHP memory does not excuse reading the whole corpus for each small result.
New measurement: Isolated QDB parity_minimal_v1 full static build at memory_limit=64M completed all four phases, producing 26 HTML files and 55 assets with a peak PHP allocation of 6 MiB. This is a tiny fixture, demonstrating baseline overhead only; it does not establish large-corpus capacity.
Boundary: A valid canonical record can be up to 16 MiB and downstream parsing/rendering can hold multiple representations. Maximum-size valid records, large threads and commits require separate tests before adopting a blanket lower limit. No content-size limits or server settings changed.
Related assessment: load_before_selection_audit_step1_solution_assessment.md proposes a separate codebase-wide investigation of selecting after whole-collection work; it includes non-memory costs and preserves overlap with this audit.
