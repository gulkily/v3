The intended result is that registering an independent identity does work proportional to that identity's records and dependencies, while preserving canonical identity, approval, authorship, and publication rules.

- [ ] **REG-07 — Compute profile changes explicitly.** Compare derived approval, attribution, and count fields with stored values. Update only profiles whose fields changed rather than issuing an update for every identity.
- [ ] **REG-08 — Remove the all-profile activity loop.** Refresh activity only for the newly linked identity and identities with changed public attribution or approval. Use the computed approval values instead of loading them again per profile. Verify unrelated activity remains untouched.
- [ ] **REG-09 — Verify the intermediate improvement.** Repeat the baseline and query-plan checks after indexing and targeted updates. Record remaining time spent loading all posts, deriving approvals, and counting profiles; do not treat the index alone as completion.

- [ ] **REG-10 — Distinguish registration from historical linking.** Define when an identity is independent and new versus connected to existing posts, bootstrap records, seeds, approvals, or invitations. Do not infer independence merely because its profile row is absent.
- [ ] **REG-11 — Implement the independent-registration path.** Create the profile, bootstrap records, username route, applicable approval state, counts, and attribution without loading every post or refreshing every profile. Preserve hidden-bootstrap counting and username-routing rules.
- [ ] **REG-12 — Bound historical authorship updates.** Locate affected posts and activity through indexed identity/bootstrap lookups. Recompute counts for affected owners, including legacy bootstrap ownership and deduplication rules.
- [ ] **REG-13 — Propagate approval changes through dependencies.** Define and implement the lookup/index strategy for approval and invitation dependencies. Use a deduplicated worklist of affected identities, preserving deterministic ordering, canonical acceptance evidence, and termination in the presence of cycles. Apply the schema contract to any additional derived structures.
- [ ] **REG-14 — Eliminate repeated invitation replay.** Avoid sorting/replaying the same unrelated post history on each approval pass. Reuse validated candidate evidence within the operation or maintain dependencies with explicit invalidation rules.
- [ ] **REG-15 — Make artifact invalidation follow actual effects.** Identify all pages affected by changed profiles, approval, attribution, or counts. Invalidate those artifacts without missing transitive changes or unnecessarily invalidating unrelated presentation.

- [ ] **REG-16 — Validate the incremental starting point.** Check that the model represents the expected canonical parent before applying the new write. Define reconciliation for mismatched heads; never mark skipped canonical changes as indexed merely by updating metadata.
- [ ] **REG-17 — Reduce the critical section safely.** Move expensive preparation outside the write lock where safe, then revalidate mutable acceptance inputs under the lock. Preserve canonical serialization, authorization, and transaction boundaries. Coordinate retraction/publication changes with the simplification handoff; do not entrench current guards as permanent requirements or remove them without an agreed replacement.
- [ ] **REG-18 — Replace unbounded request-time rebuild fallback.** Specify an observable, deduplicated maintenance path for incremental failure. Clearly distinguish a rejected write from a canonical write that succeeded while derived state remains pending. Handle candidate validation, repository advancement, promotion, and interrupted recovery.
- [ ] **REG-19 — Make retries safe.** Cover duplicate preparation/finalization, competing registration requests, and retries after canonical commit but before SQLite commit. Reuse the intended identity and avoid duplicate bootstrap records or false success metadata.

- [ ] **REG-20 — Verify semantic equivalence.** Test new and historical identities, approval seeds, transitive approvals, invitation redemption, hidden bootstrap records, usernames, profile counts, and activity authorship. Verify registration against the supported retraction behavior, tracking the intended simplification separately rather than making old immediate-suppression behavior the permanent oracle. Compare with canonical expectations and a full rebuild; resolve discrepancies rather than assuming either implementation is correct.
- [ ] **REG-21 — Verify concurrency and failure recovery.** Exercise competing writers, readers during registration, failures around each commit boundary, and repository changes during candidate building/promotion. Check that locks release and recovery is observable.
- [ ] **REG-22 — Verify scaling and reader availability.** Grow unrelated identities, posts, and activity independently. Check operation counts and query plans as well as elapsed time. Under controlled registration traffic, verify `/` and `/users/` avoid registration-induced busy responses within the supported workload.
- [ ] **REG-23 — Verify migration and delivery.** Test previous-schema startup, CLI/web configuration agreement, candidate promotion, and interrupted maintenance. Document how to deploy the schema change without surprising visitors with a large automatic rebuild. Record supported code/schema compatibility and recovery steps.
