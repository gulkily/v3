Finding: Parallel local reading passes latency criteria but requires substantial aggregate memory
Workload: 18 independent 30-second windows, three repeats each at 1/2/4 clients with and without one normal rebuild; each client has its own persistent PHP server process. 10000-record corpus, /latest, exact ordered 25-ID check on every response.
Outcome: 4627 requests, zero errors, full-window p95 at most 0.793 seconds; during-maintenance p95 at most 0.851 seconds. All rebuilds complete and post-window full synthetic body/count parity passes.
Read-only throughput ranges: 1 client 6.06-6.32 requests/s; 2 clients 6.96-11.51; 4 clients 7.93-11.00.
Rebuild-overlap throughput ranges: 1 client 3.87-5.10 requests/s; 2 clients 7.95-9.58; 4 clients 12.16-12.85.
Maximum sampled aggregate RSS: Read-only 148.5 / 253.7 / 461.6 MiB at 1/2/4 clients; overlap 278.5 / 386.3 / 599.2 MiB. Includes client driver, PHP and observed descendants; shared mappings may be counted twice and short-lived processes can be missed.
Interpretation: Overlap running faster than some baselines is variability, not evidence that rebuilds improve throughput. Baseline/overlap phases were not interleaved and background host activity was uncontrolled. No sustainable production requests/s, FPM pool size or linear concurrency extrapolation follows.
Evidence: s6-results.txt; s6-baseline-*.log.txt; s6-overlap-*.log.txt; s6-samples.txt
